Control design plan - June 15, 2026

Modernize Control around Liquid Glass without losing operational density.

The target is not a decorative skin. Control should feel closer to the newest Music-style macOS glass controls: translucent search and choice surfaces, richer background depth, stronger focus states, and queue-oriented workflows. Dense repository data stays flat, fast, and readable.

North star

Use Liquid Glass as a control material, not a page material. Search, buttons, menus, chips, and selected tab affordances can bubble; file trees, README/code content, right rails, queues, and logs should sit in flatter panes with subtle dividers.

Decision bias

Favor native macOS material and tokenized primitives over route-local glass effects. The plan preserves performance by avoiding backdrop blur on every repeated row or large content pane.

Reference Cues

  • Keep: Control's persistent sidebar, dense repository routes, right rail, and stable row heights are the right structure for a developer tool.
  • Change: Current screenshots read as a dark blue slab. Music uses depth, transparency, rim light, and content color to prevent one-note surfaces.
  • Translate: Music's playback queue becomes Control's review queue rail, repository action group, or command queue. It should not become a glossy bottom control strip or a stack of large glass cards.
  • Avoid: Full-window blur, decorative glass on repeated rows, giant cards, footer bars, boxed page sections, and translucent code/markdown content that harms contrast.

Design Decisions

The modernization should be implemented as a visual system, then rolled route by route.

  • Glass placement: search capsules, icon buttons, toolbar buttons, dropdowns, segmented choices, selected tabs, small chips, command palette, popovers, and compact action groups.
  • Flat placement: sidebar columns, file trees, code, markdown, right rails, review queues, checks, tables, logs, repeated rows, virtualized lists, and benchmark surfaces.
  • Card reduction: avoid boxed page sections and nested cards. Prefer continuous panes, hairline separators, selected-row fills, and colored status rails.
  • Queue model: introduce shared review queue and repository action primitives for the right rail and header chrome. Do not add one-off bottom bars in repository, mailbox, or local repo flows.
  • Controls: standardize search capsules, segmented controls, icon buttons, status chips, and command rows using existing shared primitives in src/renderer/src/components/ui.
  • Color: move away from single-hue blue by mixing neutral glass, graphite, white highlights, green status, amber attention, and sparse pink/blue focus glow.
  • Accessibility: expose glass strength controls through existing settings. Reduced and solid modes must stay visually distinct and readable.

Implementation Plan

The order below minimizes visual churn and keeps the app shippable after each phase.

1

Baseline and native material matrix

  • Capture native Electron screenshots for focused and unfocused states.
  • Repeat for light solid, dark solid, dark reduced, and dark glass shell.
  • Verify neutral, blue, and yellow wallpaper/backdrop behavior.
  • Keep src/main/theme/liquidGlassOptions.ts as the native option boundary.
2

Material tokens and primitives

  • Add semantic tokens for glass controls, flat panes, dividers, selected rim, focus glow, row, and content.
  • Extend shared primitives rather than styling each route locally.
  • Ensure repeated rows and large panes never get backdrop blur.
  • Audit dark mode first with rg color and radius checks from the WIP plan.
3

Shell, sidebar, and top search

  • Give top search the focused glass-lens treatment from the reference.
  • Keep sidebar as an integrated pane; use restrained selected-row fills rather than card cells.
  • Normalize icon button sizes and titlebar hit regions.
  • Keep the renderer root transparent on macOS so native glass remains visible.
4

Command palette as first flagship surface

  • Implement the Concept C search overlay with segmented scope choices.
  • Use grouped command rows and a preview rail for repository, issue, PR, file, and action results.
  • Keep keyboard navigation, focus rings, and result virtualization intact.
  • Use this as the proving ground before touching every route.
5

Repository chrome and working set

  • Modernize repository tabs, branch/ref picker, filter bars, and right rail controls.
  • Move Sync, Review, Run checks, and Open in IDE into repository header actions and right-rail queue actions.
  • Flatten file tree, README, review queue, checks, and issue rows into integrated panes.
  • Apply first to Code and Issues, then Pull Requests and Actions.
6

Mailbox and queue unification

  • Rework Mailbox as the account-level review queue.
  • Share filters, segmented chips, notification row actions, and queue actions with repository routes.
  • Keep unread, in-app, muted, stale, and attention states tokenized.
  • Use Mailbox to validate high-volume row performance.
7

Settings and accessibility controls

  • Add glass strength or opacity choices under Appearance if native APIs and CSS fallback support it.
  • Keep solid, reduced, and glass shell modes predictably distinct.
  • Verify high contrast, reduce transparency, and reduced motion scenarios.
  • Document platform limitations when Electron/native APIs cannot match system Music behavior.
8

Validation and review

  • Run bun run format, bun run lint, and bun run typecheck.
  • Run bun run test for changed shared logic.
  • Use renderer screenshots for route regression and native app screenshots for glass behavior.
  • Use react-doctor . --offline and react-scan only when render cost is suspect.

--color-glass-control Search, segmented controls, icon buttons, toolbar pills. Low-alpha glass with visible border and hover state.
--color-pane-canvas Sidebar, file tree, README, right rail, checks, and metadata areas. Flat, low-alpha pane treatment with hairline separators instead of glass cards.
--color-content-row File, issue, mailbox, notification, and PR rows. No backdrop blur; high contrast; stable row height.
--color-selected-rim Selected nav, selected tab, selected search scope. Use outline/glow before using solid fill.
--shadow-glass-float Command palette, popovers, menus, and transient overlays. Deep enough to separate glass from dense data behind it.
--radius-liquid-control Pills, search capsules, queue actions. 999px for capsules, fixed dimensions for icon buttons.

Acceptance Criteria

The redesign is done when it is more native, not just more translucent.

  • Visual: top search, segmented choices, command palette, and repository action groups visibly share one Liquid Glass control system.
  • Material restraint: glossy bubble glass appears only on floating controls and transient UI. Large app regions use flat panes, not cards.
  • Operational: repository rows, files, code, markdown, logs, and tables remain more legible than the current screenshots.
  • Performance: high-volume lists do not add per-row blur, expensive filters, or layout shifts.
  • Modes: solid, reduced, and glass shell modes have distinct screenshots in light and dark.
  • Native: focused/unfocused macOS windows do not drift toward cyan, yellow, or wallpaper casts.
  • Validation: formatter, linter, typechecker, and relevant tests pass before merging code changes.
